站点构建出来的产物只有 3.8M，说实话已经不算大。但「不大」和「没有优化空间」是两回事。这轮我没有去动框架和构建配置，而是先扫了一遍内容质量，确认没有硬伤之后，才把力气花在三处能拿出数字的地方：截图格式、缓存策略、第三方预连接。

顺序很重要。性能优化最容易犯的错，是去优化一个本身内容就有问题的页面——图没压缩、描述乱写、链接失效，这时候再怎么调缓存也只是把问题送得更快。所以先做内容体检，是我给自己定的前置条件。

## 先做内容体检，再谈性能

体检脚本查了四件事：frontmatter 必填字段是否完整、图片有没有 alt、正文是否越级使用 H1、站内链接是否指向存在的路由。三篇文章加十二个项目扫下来，硬性问题零：描述齐全、alt 齐全、死链为零、标题层级正确。

顺带核对了截图声明的宽高和图片真实像素——九张图逐一用 sharp 读取，全部一致。这一步看着和性能无关，其实是在保护后面的优化：宽高属性是防止布局偏移（CLS）的关键，如果一开始数据就是错的，把图换成 WebP 也不会让页面更稳。

体检通过，才进入正题。

## 第一件事：把截图从 JPG 换成 WebP

项目详情页里有四张 navmate 的界面截图，还是 JPG 格式，加起来 663 KB，占了整个图片目录的一半以上。这类长截图有个特点：横向很宽、色彩层次不多，正是 WebP 擅长压缩的场景。

用项目里已有的 sharp 转了一遍，quality 设 82：

| 图片 | 原 JPG | WebP | 节省 |
|---|---:|---:|---:|
| 首页搜索 | 238K | 58K | 76% |
| AI 工具分类 | 177K | 57K | 68% |
| 办公与设计 | 121K | 36K | 70% |
| 开发与影音 | 127K | 40K | 69% |
| **合计** | **663K** | **191K** | **71%** |

转换时特意确认了输出尺寸与源图完全一致（比如首页搜索还是 3651×1100）。这一步不能省：frontmatter 里已经写好了宽高，尺寸一变，防 CLS 的声明就和实际对不上了。尺寸不变，引用改一下扩展名，旧 JPG 删掉，就收工。

## 第二件事：给图片和 OG 图补上缓存

线上实测发现，`/images/*` 和 `/og/*` 走的是全局默认缓存头：

```
cache-control: public, max-age=0, must-revalidate
```

这意味着每次访问都要回源校验一次。对于几乎不变的图片来说，这是纯浪费。补上配置：

```
/images/*
  Cache-Control: public, max-age=86400

/og/*
  Cache-Control: public, max-age=86400
```

为什么是 1 天，不是 1 年？因为这些文件名里没有内容 hash。如果直接设成 `immutable`，哪天换张图，用户可能几个月都看不到新版。86400 秒是个折中：既避免每次回源，又把陈旧窗口压在一天内。我在配置文件里把这条约束写进了注释——以后谁想改缓存策略，先看到的就是「改图要换文件名」这个前提。

真正需要长期缓存的是带 hash 的资源，比如 `_astro` 目录下的 CSS 和 JS，那边已经是 `max-age=31536000, immutable`，不用动。

## 第三件事：给评论区预连接

评论用的是 Giscus，加载时要连到第三方域名。此前没有任何预连接提示，每次都要完整走一遍 DNS 查询加 TLS 握手。

在评论组件顶部加一行就够了：

```html
<link rel="preconnect" href="https://giscus.app" />
```

这个组件被文章页、项目页和留言页共用，一处改动覆盖三个入口。省下的是一次跨站握手，单看不多，但它是每篇有评论的页面都要付的成本。

## 顺手审查的并行改动

提交时发现工作区里还有另一路会话留下的改动，没有直接忽略，而是逐项审了一遍：CMS 图片控件加了 `choose_url: false` 禁止外链图、schema 把非法链接归一为「未提供」避免后台输入打挂构建、图片引用校验改用发布闸门口径。方向与这轮优化兼容，就一起纳入了。

多会话并行改同一个仓库时，「先看清楚再提交」比「各改各的」重要得多。否则一次 `git add -A` 就可能把没验证过的东西带上车。

## 验证：别只凭感觉说变快了

性能改动最容易自我感觉良好，所以每一步都用数字收口：

- 类型检查 0 error，主测试集 91/91，构建冒烟 15/15；
- 全站巡检 39 个页面（37 个 sitemap 页面 + 搜索页 + 404 页）零失败；
- 线上抽查 WebP 返回 200、`content-type: image/webp`、`cache-control: max-age=86400` 生效，旧 JPG 返回 404；
- 产物总体积从 3.8M 降到 3.4M，图片目录从 1.2M 降到 760K。

部署后 CI 两条工作流全绿，线上页面和本地产物核对一致。

## 几点经验

第一，优化前先问「有没有更基础的问题」。内容扫描没发现问题，才让后面的性能改动有一个干净的基线。

第二，能量化的收益才值得写进提交信息。「省了 71%」比「大幅减小体积」有用得多，后来复盘时不用重新测一遍。

第三，缓存时间不是越长越好。文件名不带 hash 的资源，缓存策略要考虑更新路径，否则优化会变成下一次排障的起点。

第四，多会话协作时，提交前把不属于自己的改动审一遍。这次并行改动方向一致所以并入了；不一致的时候，宁可分两个提交。
