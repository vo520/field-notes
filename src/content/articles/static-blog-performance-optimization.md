站点产物只有 3.8M，说实话不算大。但「不大」和「没有优化空间」是两回事。这篇按「目标 → 路径 → 边界 → 呈现 → 落地」五步，把这一轮优化拆开讲清楚——它更像一次工程决策的记录，而不是一串随手改的配置。

## 1. 用户要完成什么

先把「用户」拆成两层，否则很容易优化错方向。

**访客要完成的事**：打开文章或项目页，尽快看到正文和截图，中途界面不跳动，评论区不拖慢首屏。访客不关心产物体积，只关心「点开之后等多久、页面稳不稳」。

**维护者要完成的事**：在不改框架、不动构建配置的前提下，把体积和重复请求降下来，而且每一处改动都要能拿出数字、能回滚。 「感觉变快了」不算交付。

由此定下三条目标：

- 产物总体积明显下降，且收益可量化；
- 视觉与交互零变化——尤其不能引入布局偏移（CLS）；
- 缓存策略可控，不留「改了图用户半年看不到」的隐患。

还有一条前置条件：**先确认内容本身没有硬伤**。优化一个描述乱写、链接失效的页面，只是把问题送得更快。所以体检先于性能，这条不可跳过。

## 2. 页面要怎么走

这轮的执行是一条单向链路，每一步都是下一步的前提：

**第一步，内容体检。** 脚本扫四件事：frontmatter 必填字段、图片 alt、正文是否越级用 H1、站内链接是否指向存在的路由。复盘时点扫的三篇文章加十二个项目，硬性问题零。顺带用 sharp 读取九张截图的真实像素，与 frontmatter 声明的宽高逐一比对，全部一致。

**第二步，截图瘦身。** 项目详情页有四张 navmate 界面截图还是 JPG，合计 663 KB，占整个图片目录一半以上。长截图横向宽、色彩层次少，正是 WebP 擅长的场景。用项目已有的 sharp 转换，quality 82：

| 图片 | 原 JPG | WebP | 节省 |
|---|---:|---:|---:|
| 首页搜索 | 238K | 58K | 76% |
| AI 工具分类 | 177K | 57K | 68% |
| 办公与设计 | 121K | 36K | 70% |
| 开发与影音 | 127K | 40K | 69% |
| **合计** | **663K** | **191K** | **71%** |

**第三步，补缓存策略。** 线上实测 `/images/*` 和 `/og/*` 走的是全局默认头 `max-age=0, must-revalidate`，每次访问都回源校验。对几乎不变的图片来说是纯浪费，补上 1 天缓存。

**第四步，预连接第三方。** 评论区用 Giscus，加载时要连 `giscus.app`，此前没有预连接提示，每次都完整走一遍 DNS 加 TLS 握手。

**第五步，验证与上线。** 每一步都用数字收口，再推上线。

这条链路的核心不是「先做哪件事」，而是**先排除内容问题，再动传输层，最后验证**——顺序反了，优化就可能建立在错误基线上。

## 3. 空和失败怎么处理

性能优化里真正需要想清楚的，是各种「万一」。

**万一图片尺寸对不上。** 转 WebP 时特意保持输出尺寸与源图完全一致（首页搜索仍是 3651×1100）。frontmatter 里已写好宽高，尺寸一变，防 CLS 的声明就和实际对不上——图是变小了，页面却开始跳。这是最容易被忽略的失败态。

**万一缓存撑到用户看到旧图。** 文件名不含内容 hash，所以没有设 `immutable`，只给 `max-age=86400`。陈旧窗口压在一天内，代价可控；真要立刻更新就换文件名。约束直接写进配置注释，避免下一个人踩坑。真正能长期缓存的是带 hash 的 `_astro` 资源，那边本来就是 `immutable`，不用动。

**万一旧文件没删干净。** 旧 JPG 用 `git rm` 移除，线上抽查返回 404 是预期结果，不是故障。留着无引用的死产物，下次盘点还得再判一次「这个还用不用」。

**万一体检没过。** 那就停在这里——先修内容，不进入性能步骤。本轮体检通过才继续。

**万一有并行改动。** 提交时发现工作区还有另一路会话的改动，没有 `git add -A` 一把梭，而是逐项审：CMS 图片控件加 `choose_url: false` 禁外链图、schema 把非法链接归一为「未提供」防构建打挂、图片引用校验改用发布闸门口径。方向兼容才一起纳入；不兼容就分开提交。

**万一要回滚。** `git revert` 即可，但得说清范围：性能部分只涉及缓存头、预连接、截图引用和四张图，混在提交里的并行改动不在其中。边界写清楚，回滚才不会误伤。

## 4. 界面为什么要这样排版

这里的「排版」不只是视觉，更是**信息怎么呈现才让人能判断**。

**截图区保持桌面外框、宽高占位。** 九张截图全是 desktop，画廊的桌面样式是默认路径；宽高属性让浏览器在图加载前就留出空间。上一轮还修过一处文案不一致——导语原本写「桌面端与移动端」，实际没有移动端截图，已改为只提桌面。界面说什么，就得真有什么。

**收益用表格，不用形容词。** 「省了 71%」比「大幅减小体积」有用得多。逐图列出转换前后，读者能自己核对，复盘时也不用重测。

**配置放在代码块里，可直接复制。** `_headers` 和 `preconnect` 以最小可行片段呈现，不夹杂上下文噪音——看到就能贴。

**约束写在注释里。** 缓存头上方注明「文件名不含 hash，改图需换名才即时生效」。把决策理由留在代码旁边，比写在文档里更容易被看见。

**文章按五段式分节。** 从「要完成什么」到「代码怎么落地」，给读者一条明确的心智路径。技术方案的说服力，一半来自结论，一半来自推导过程可复现。

## 5. 最后代码怎么落地

改动全部收敛在四个文件，加一组图片：

| 文件 | 改动 |
|---|---|
| `src/content/projects/navmate.md` | 4 条 `screenshots[].src` 改 `.webp`，宽高字段不变 |
| `public/images/projects/navmate/*.webp` | 新增 4 张 WebP，旧 JPG 用 `git rm` 移除 |
| `public/_headers` | `/images/*` 与 `/og/*` 加 `max-age=86400`，附约束注释 |
| `src/components/GiscusComments.astro` | 顶部加 `<link rel="preconnect" href="https://giscus.app" />` |

核心代码就两段。缓存配置：

```
/images/*
  Cache-Control: public, max-age=86400

/og/*
  Cache-Control: public, max-age=86400
```

预连接：

```html
<link rel="preconnect" href="https://giscus.app" />
```

转换命令用项目已有的 sharp，不引入新依赖：

```js
await sharp(src).webp({ quality: 82, effort: 6 }).toFile(out);
```

**验证结果**：`astro check` 0 error、主测试 91/91、构建冒烟 15/15、全站巡检 39 页零失败；线上 WebP 返回 200 且缓存头生效，旧 JPG 返回 404；产物 3.8M → 3.4M，图片目录 1.2M → 760K。CI 两条工作流全绿后上线。

一句话收尾：**先定义清楚用户要完成什么，再让每一步改动都能回答「失败了怎么办」，最后用数字证明它真的发生了。**
