这个预约模块不是原型稿，而是跑在微信小程序里的真实业务：访客到越疆展厅参观，需要先选工作日时段、填写来访信息、上传人脸，提交后拿到预约记录和签到二维码。

我把五件事按顺序讲清楚：用户要完成什么、页面怎么走、空和失败怎么处理、界面为什么这样排、最后代码怎么落地。文中路径和字段都来自 `pages/visit/*.vue` 与 `api/index.js`。

## 1. 用户要完成什么

用户的目标只有一句话：**在某个工作日的一个连续时间段里，把自己的来访信息报备给公司，并在到访时出示二维码签到。**

拆开看是四步：

1. 选日期和时段。可选范围是工作日 09:00–18:30，每 30 分钟一段，12:30–14:00 午休不开放。
2. 填表单。包括来访企业、主要来访人姓名、手机号、来访目的、同行人数、受访者、到访地址、到访楼层、是否停车与车牌、备注，以及一张必填的人脸照片。
3. 提交。一个连续时段生成一条预约；相邻时段会合并，跨上午/下午则拆成多条。
4. 到访。在「我的预约记录」里看状态，开始前 2 小时内可以打开签到二维码。

到访企业是固定的「越疆机器人」，用户选的是楼层，最终展示为「越疆机器人 · 16楼」这种形式。来访企业则是访客自己所属的公司，需要用户搜索或填写。

## 2. 页面要怎么走

`pages.json` 里注册了五个页面：

| 页面 | 作用 |
| --- | --- |
| `pages/visit/index` | 选日期、选时段、看展厅信息 |
| `pages/visit/submit` | 填访客信息、上传人脸、提交 |
| `pages/visit/record` | 我的预约记录，按状态分组 |
| `pages/visit/detail` | 单条预约详情与操作 |
| `pages/visit/qrcode` | 签到二维码与有效窗口提示 |

主链路是 `index → submit → record → detail → qrcode`，但中间有几个真实的回环。

### 选时页到提交页：用本地缓存传参

时段可能选很多个，塞进 URL 不合适。选时页在跳转前把选择写进 `visitTimeSelection`：

```js
uni.setStorageSync("visitTimeSelection", {
  date: d.getTime(),      // 选中日期的零点毫秒
  dateText: "11月28日（周五）",
  periods: [{ label: "09:00-09:30", startTime, endTime }]
});
uni.navigateTo({ url: "/pages/visit/submit" });
```

提交页 `onLoad` 读这个键，恢复时段和日期；读不到就提示「预约时段已失效，请返回重选」，不允许空着表单继续填。

### 提交页到记录页：成功才消费

全部时段创建成功后，提交页做三件事：把新记录写进本地、缓存本次表单、删掉 `visitTimeSelection`，然后 `redirectTo` 记录页。这样用户从记录页返回时，不会回到一个已经提交过的提交页。

### 部分成功：留在提交页，把剩余时段写回去

如果一次选了 4 段，前 2 段创建成功、第 3 段失败，提交页不会假装全部成功。它会把已成功的 2 条落盘，把剩下的 2 段重新写回 `visitTimeSelection`，并提示「已成功提交 2/4 条，剩余 2 条可重试」。用户返回选时页时，`onShow` 里的 `syncSelectionFromStorage()` 会按缓存恢复选中态，避免重复提交已经成功的时段。

### 已有预约：先拦一次，再拦一次

选时页点提交时，会先用 `ensureVisitIdentity()` 确认身份，然后扫本地记录找「活动预约」：排除已取消/已签到、排除待审批/已拒绝、排除 `endTime` 已过期、排除还没进入二维码有效窗口的记录，并且只比较同一个日历日。命中就弹窗「已有进行中的预约」，让用户选「查看签到」或「继续预约」。

提交页在真正发请求前还会再查一次，按手机号匹配本地记录。这不是重复代码，而是两个入口的防重复：选时页拦的是「从首页重新选时间」，提交页拦的是「用户停留在提交页反复点保存」。

## 3. 空和失败怎么处理

这个模块大部分工程量都在异常路径上。

### 没有可选日期或时段

- 日期条只生成未来 7 个 `isWorkday` 的工作日；周末、法定节假日不会出现，补班日会出现。
- 如果今天所有时段都已经开始，默认选中下一个工作日，而不是让用户点进一个全灰的今天。
- 跨天时日期列表整体前移，单靠 `selectedDateIndex` 会指到另一天，所以代码用 `selectedDateTs` 记录绝对日期，重建列表后把索引拉回来；原日期已经不在 7 天窗口内就清空选择。
- 用户没选日期、没选时段、选了过去的日期，分别给三句不同的 toast，而不是一句笼统的「请完善信息」。

### 时段只能连续选

用户可以多选，但必须是时间轴上连续的一段。午休 12:30–14:00 被硬屏蔽，所以「上午最后一段 + 下午第一段」是允许的，中间跳过的部分必须正好落在 `blockedRanges` 里。

不满足时，代码不会保留原来的选择再叠加，而是清空、只留下新点，并提示「只能选择连续时段」。这样用户看到的高亮永远和最终会提交的时段一致。

### 今天已经开始的时段不能选

魔点创建访客预约要求 `startTime` 不早于当前时间。所以禁用判断按**开始时间**做，而不是结束时间：

```js
isPeriodDisabled(index) {
  const d = this.selectedDate;
  if (!d) return true;
  const todayZero = new Date(now.getFullYear(), now.getMonth(), now.getDate()).getTime();
  if (d.getTime() !== todayZero) return false;
  return this.buildTimestamp(d, this.periodList[index].start) <= Date.now();
}
```

提交页还会再校验一次，因为用户可能在表单页停留很久，选的时候还没开始、点保存时已经开始了。

### 表单校验

提交前的校验顺序是固定的：先企业、楼层、姓名、手机号，再目的、同行人数、受访者、地址，最后才是人脸和备注。几个容易漏的点：

- 姓名、来访目的、备注共用一条字符白名单 `CN_EN_DIGIT_RE`，只允许中英文、数字、常见间隔符和空格。特殊符号提交到魔点会返回格式错误。
- 手机号必须是 `1` 开头的 11 位。
- 同行人数必须是 1–99 的整数。
- 停车时才校验车牌；油车按 7 位、新能源按 8 位分别用不同正则，最多 5 辆。
- 人脸是必填项，没有照片不允许提交。

### 提交失败

创建阶段逐段调用 `visitCreateApi`。如果接口没返回 `visitRecordId` 或 `appointmentId`，直接抛错，不落本地记录——否则记录页会留下一条无法取消的脏数据。

- 全部失败：把后端返回的 `message` 透出来，而不是只说「提交失败」。
- 部分成功：已成功的落盘，剩余时段回写，提示用户重试剩余部分。
- 人脸绑定：放在创建成功之后单独做，失败不阻塞主流程。绑定失败会提示「预约创建成功，N 段人脸可后续补录」，并针对「人脸过小」给出重新裁剪的建议。

### 记录页的状态不是魔点状态

直连方案下，魔点创建接口不返回预约状态，所以记录页用本地字段推导：

- `2` 已取消、`3` 已签到是终态；
- `4` 是本地伪状态，表示时段已过或取消接口返回 `010190129`（预约已结束）；
- `1` 已创建还要叠加 `auditStatus`：`1` 显示待审批，`2` 审批通过，`3` 审批拒绝。

待审批的记录不显示取消按钮，因为魔点后端会拒绝取消并返回 `010190196`。与其让用户点了再报错，不如一开始就不给入口。

### 二维码的有效窗口

二维码不是创建后立刻能扫。`checkQrValidWindow` 把有效窗口定义为 `[startTime - 2 小时, endTime]`：

- 早于窗口：`tooEarly`，页面提示还没到签到时间；
- 晚于 `endTime`：`tooLate`，提示预约已结束；
- 没有时间字段：不阻断，按默认有效处理。

## 4. 界面为什么要这样排版

### 选时页：先让用户看清「能不能约」

页面顶部是展厅大图和展厅信息卡，下面是详情说明，再往下才是日期和时段。这个顺序不是装饰：用户先确认「我要去的地方对不对」，再决定「什么时候去」。

- 返回按钮是自绘的，垂直中心和微信胶囊对齐；因为页面用了 `navigationStyle: custom`，系统返回键不可用。
- 展厅头图从 banner 接口取 `bannerId=6`，失败时保留本地占位图，不让页面出现破图。
- 地址卡有导航按钮；经纬度还没配置时，点击改为复制地址，并提示「地址已复制，可在地图中搜索导航」。
- 日期用横向滚动条，配一个日历入口；下面有时段网格和「全选 / 清空」。
- 午休被移除后，第二段之前会渲染一条分隔线和「午休」标签，用户能看懂为什么 12:30 后面直接跳到了 14:00。
- 已开始的时段是禁用态，但仍然显示，用户知道这个时间段存在，只是今天约不了。
- 底部是固定的 `JMainBtn`，文案「预约/提交记录」。内容区留出 `safeBottom`，避免最后一行被按钮压住。

### 提交页：按填写心智排序

表单顺序是：预约时段 → 来访企业 → 姓名 → 手机号 → 来访目的 → 同行人数 → 受访者 → 到访地址 → 到访楼层 → 是否停车 → 备注 → 人脸。

- 最上面先回显用户选的时段，点一下可以返回重选；用户不需要记住自己选了什么。
- 必填项统一用星号标记，错误提示逐项出现，不一次性糊一屏。
- 到访企业是固定值，所以展示成「越疆机器人」加一个「固定」徽章，避免用户以为可以改。
- 到访楼层是单列滚轮。当前配置里只放了 1 楼和 16 楼两项，这是代码事实，不是文案遗漏。
- 停车开关关闭时，车牌区域直接不渲染；打开后才出现省份前缀和车牌输入行，支持添加/删除多辆。
- 人脸卡放在最后，但它不是可选项。选图后强制进入裁剪，输出至少 200×200 的方图，从源头满足魔点的人脸尺寸要求。

### 记录页：状态分组比时间排序更有用

记录页顶部是「全部 / 活跃 / 已结束」三个 tab，带数量。用户打开记录页通常只想回答两个问题：我接下来有没有预约、我上次的预约结束了没有。

- 活跃 = 已创建且未过期；
- 已结束 = 已取消、已签到、已结束；
- 空态文案也分 tab：「暂无活跃预约」「暂无已结束记录」「暂无预约记录」。
- 卡片底部操作按状态显隐：活跃记录可以看二维码、补人脸、取消；终态记录只能删除本地记录。
- 状态条颜色按语义分：待审批是黄色，已签到是绿色，已取消是红色，已结束是灰色。

## 5. 代码怎么落地

### 时段配置只有一处

营业时间、步长、午休都写在 `index.vue` 顶部，模板和计算属性都从它生成：

```js
const PERIOD_CONFIG = {
  startTime: "09:00",
  endTime: "18:30",
  stepMinute: 30,
  blockedRanges: [["12:30", "14:00"]]
};
```

`buildPeriodList()` 负责切段，`isBlocked()` 用半开区间判断重叠；如果某一段前面跳过了屏蔽区间，就给这段打上 `showDividerBefore`，模板据此画午休分隔线。

### 连续选择用时间轴判断，不用索引

`togglePeriod()` 先把候选按开始时间排序，再交给 `_isContiguousWithBlocked()`。它从第一段走到最后一段，逐个 30 分钟槽位检查：要么在候选里，要么被 `blockedRanges` 覆盖。这样即使以后把午休从「硬移除」改成「禁用但保留」，判断逻辑也不用重写。

### 提交页的两阶段

第一阶段只创建预约，逐段请求；第二阶段才绑人脸。创建成功后立刻 `persistCreated(created)`，避免人脸阶段异常退出导致「预约创建了但本地没记录」。

人脸绑定用固定并发 2 的 worker 池，每条预约独立标记 `faceUploaded`。失败项不会污染 `faceImagePath`，记录页因此不会出现「有缩略图但还要补录」的矛盾状态。

### 本地记录写入统一走串行队列

提交页、记录页、详情页、二维码页都会改本地记录。如果各自做「读—改—写」，页面栈共存时异步回调可能互相覆盖。`api/index.js` 里用一个 Promise 队列把所有写入串行化，`patchVisitRecord()` 按 `appointmentId / visitRecordId / id` 做 upsert：

```js
let _writeQueue = Promise.resolve();
function _serialWrite(fn) {
  _writeQueue = _writeQueue.then(fn, fn);
  return _writeQueue;
}
```

这解决的是真实的 RMW 竞态：记录页刚同步完状态，二维码页的补码回调晚到，不应该把状态改回去。

### 防连点不是加个 disabled 就够

选时页用 `navigating` 和 `checking` 两个标志：前者守 `navigateTo` 的异步窗口，后者守 `ensureVisitIdentity()` 的网络窗口。两者都配了 3 秒兜底复位，因为页面栈满或 `complete` 不触发时，按钮不能永久失效。

提交页则用 `submitting` 加 `try...finally`，所有 early return 和成功跳转都会复位。这样不会出现「点了一次失败后按钮再也点不动」。

还有一个很具体的小坑：微信 `showModal` 的 `confirmText` 最多 4 个汉字。最初写的「查看签到码」是 5 个字，弹窗直接不显示；改成「查看签到」后才正常。

---

这套代码没有把预约做成一个「万能表单」，而是把约束放在最前面：哪些日期能约、哪些时段连续、什么算重复预约、什么算提交成功。界面只是这些规则的投影。规则写清楚了，空态、失败提示和按钮显隐才有统一的依据。
