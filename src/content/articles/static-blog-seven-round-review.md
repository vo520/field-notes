上一篇文章整理了自查清单，这一篇按轮次记录过程。每轮只解决一类问题，改完立刻验证，再进入下一轮。分轮的价值不在于「看起来有条理」，而在于每次改动的影响范围可控，出问题也容易定位是哪一轮引入的。

## 第一轮：先修能直接感受到的问题

按 P0 处理，标准是「用户会立刻遇到」。

移动端菜单在手机上跑到页面中间，原因是头部用了 `backdrop-filter`，它创建了包含块，里面的 `position: fixed` 不再相对视口定位。改成 `position: absolute`，相对头部展开，问题消失。

首页原本展示的项目和分类过多，收敛到三个代表性项目；项目筛选器也不再渲染没有项目的空分类，避免点了没反应。

**这一轮的经验**：先修「看得见」的问题，但不要停在表象。菜单错位看起来是坐标问题，根因是 CSS 包含块；空分类看起来是数据问题，根因是渲染前没有按实际数量过滤。

## 第二轮：结构、抓取与测试覆盖

这一轮处理 P1：搜索引擎和辅助技术如何看待页面。

每页保证恰好一个 `h1`，标题层级不跳级；项目详情页补上 `og:image`，分享时有图；同时梳理测试分层，把构建产物的断言和纯函数测试分开，避免某些用例因为脚本入口没覆盖而长期漏跑。

**这一轮的经验**：语义结构不是「顺手优化」，它同时影响 SEO、屏幕阅读器和页面大纲。测试分层也不是形式主义，跑不到的测试等于不存在。

## 第三轮：让对外输出保持一致

这一轮处理 P2 里的「对外契约」。

RSS 里的域名统一到 `site` 配置，不再残留旧域名；`lastBuildDate` 改为取内容的最大更新时间，而不是构建时刻，否则每次构建都在宣称「刚更新」。sitemap 排除 `/search/`，搜索页自身再加 `noindex`，两边成对。文章页输出 `BlogPosting`，项目页输出 `SoftwareSourceCode`，首页输出 `WebSite` 与 `Person`。搜索面板补足触控尺寸，检查对比度和 viewport。

**这一轮的经验**：同一个意图要落实到所有出口。只从 sitemap 删除搜索页，页面仍可能被外链带进索引；只改 RSS 文案，域名仍可能从 canonical 漏出去。

## 第四轮：细节语义与边界条件

P2 的尾项看起来零碎，但都关于「边界」。

主题切换从普通容器换成真正的 `<button type="button">`，带 `aria-label`，切换后同步更新文案，键盘和读屏都能用。标签转 slug 时清理 `\ / ? # % & +` 等会破坏路径的字符，同时保留中文。链接校验只接受 `http` / `https`，仓库地址额外限定 GitHub 或 Gitee 的 HTTPS 地址。

**这一轮的经验**：边界条件最适合交给 schema 和单元测试，而不是靠代码评审时的记忆。写错协议、写错字段名，应该在构建阶段失败。

## 第五轮：搜索索引的取舍

Pagefind 的规则是：一旦有页面标了 `data-pagefind-body`，没有这个属性的页面就不进入索引；一个页面可以有多段 body，内容会合并。

首页因此需要做取舍。全量索引会把项目卡片和文章卡片的标题、摘要全部收进去，和详情页大量重复；完全不索引又搜不到站点介绍。最终只给品牌文案区和开源说明区加 body，卡片区加 `data-pagefind-ignore`，`/search/` 与 404 不索引，索引页数固定为断言里的数字。

**这一轮的经验**：搜索不是「越多越好」。索引边界要按「用户想搜到什么」设计，并且用 `page_count` 断言锁住，任何页面增删都会立刻暴露。

## 第六轮：交互守卫与测试基础设施

这一轮修的是两类隐蔽问题。

第一类是输入法。按 `/` 聚焦搜索、Enter 打开结果、上下键切换，在中文组词时都会被误触发。所有键盘处理函数开头加 `if (event.isComposing) return;`，包括全局快捷键和搜索输入框。移动端菜单补上「点击外部关闭」，同时忽略头部内部的点击。

第二类是测试辅助函数本身。构建冒烟测试里残留了 ESM 环境下的 `require`，另一个测试文件直接使用了未导入的 `parseYaml` 和 `readdirSync`。这些错误平时不一定触发，一旦执行到对应分支就整条用例失败。统一改为调用共享的 `readMarkdownFrontmatter`。

**这一轮的经验**：交互问题要按输入法的真实状态设计，而不是按「按键即命令」的假设。测试代码也是代码，辅助函数同样需要类型检查和实际执行。

## 第七轮：内容沉淀与验证闭环

代码改完后，把三篇既有文章按同一标准重写：结论前置、补足机制解释、保留原有 frontmatter 和 slug。随后新增两篇记录：一篇是自查清单，一篇就是这份轮次总结。

每轮结束都跑同一套验证：单元测试、`astro check`、构建、构建冒烟测试，最后核对产物里的页面数、索引数、RSS 条数、sitemap 条目和目录锚点。

**这一轮的经验**：文档不是收尾工作，而是把过程中的判断固定下来。验证也不是「跑一遍命令」，而是知道每个数字应该是多少。

## 总结：七轮之后留下的六条原则

1. **先修感知问题，再追根因**：错位、无效点击背后通常是布局或数据过滤，不是坐标微调。
2. **语义结构一次做对**：一个 `h1`、正确的标题层级、真实存在的分享图，成本低但收益长期。
3. **对外输出成对处理**：sitemap 与 `noindex`、canonical 与 RSS 域名，必须同源同改。
4. **边界交给 schema 和测试**：协议、字段名、slug 字符集，让构建期报错而不是线上出错。
5. **索引是取舍，不是全量**：明确搜索该命中什么，再用断言锁住数量。
6. **验证要有预期值**：页面数、索引数、RSS 条数都应该能提前说出来，对不上就是有问题。

七轮下来，真正难的从来不是写某个组件，而是判断「这件事应该在哪一层解决」。层次判断对了，改动通常很小；判断错了，就会在错误的层面反复打补丁。
