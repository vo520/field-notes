很多人第一次使用 RediSearch 时，会把它理解成“把查询结果提前存在 Redis 里”，以为第二次执行同样的 `FT.SEARCH` 会直接拿到缓存。这个理解不完全准确。

## 先说结论

RediSearch 主要保存的是**索引结构**，不是每一次查询产生的完整结果集。执行 `FT.SEARCH` 时，它会根据倒排索引、数值索引、标签索引等结构找到匹配文档，再按照过滤、排序和分页条件返回当前结果。

因此，相同查询通常会重复执行，而不是自动命中一个永久保存的结果集缓存。它快，是因为“找哪些文档”这一步走的是索引，不是因为“上次的结果还在”。

## 索引中保存了什么

假设我们建立如下索引：

```text
FT.CREATE idx:article ON HASH PREFIX 1 article:
  SCHEMA title TEXT tags TAG publishedAt NUMERIC SORTABLE
```

RediSearch 会为文本词项、标签和数值字段维护适合检索的数据结构。原始数据仍然保存在 Hash 或 JSON 文档中，索引负责回答“哪些文档可能匹配”，并记录足够的信息把文档 ID 找回来。

这个分工很重要：索引是检索结构，不是文档副本。更新文档后，RediSearch 需要同步维护索引项；删除文档时，索引项也会一起清理。索引膨胀、字段类型选错、前缀范围过大，都会直接影响查询延迟和内存占用。

## 一次 FT.SEARCH 做了什么

一次查询大致会经历这些步骤：

1. 解析查询语句和参数，确定要使用的字段和过滤条件；
2. 在文本、标签、数值等索引上求交或求并，得到候选文档集合；
3. 应用数值范围、标签过滤、地理条件等约束；
4. 按 `SORTBY` 排序，或按相关度返回；
5. 根据 `LIMIT offset num` 截取当前页，再加载文档内容。

这里有两个常被忽略的优化点：

- 只关心数量时，可以用 `LIMIT 0 0` 配合 `NOCONTENT`，避免为每一页结果加载字段；
- 只需要部分字段时，用 `RETURN` 限制返回列，减少网络传输和序列化开销。

`SORTBY` 也有成本。声明 `SORTABLE` 的字段会额外保存适合排序的数据，占用内存；如果只是排序、不做范围查询，部分场景可以用 `UNF` 关闭归一化来降低开销。这些都属于索引设计，而不是结果缓存。

深分页同样值得警惕。`LIMIT 10000 20` 并不是“直接跳到第 10000 条”，前面的候选结果仍要参与排序和截断。页码越深，代价越高，通常应该改成基于游标或业务主键的翻页方式。

## 游标是不是结果集

聚合查询可以使用 `WITHCURSOR`。游标会在服务端暂时保留查询执行状态，让客户端分批读取后续数据。

它更接近“未读完的临时查询状态”，而不是长期结果缓存：

- 有空闲超时，超时后自动释放；
- 会占用服务端内存和连接资源；
- 读取完成后应该主动删除，而不是一直挂着；
- 不适合作为业务缓存键长期复用。

把游标当成缓存会带来两个问题：一是超时后数据消失，调用方必须能重新发起查询；二是并发请求各自持有游标，资源会随并发量线性增长。

## 如果确实需要保存结果

业务上需要复用昂贵查询时，可以显式建立缓存：把查询条件规范化并计算哈希，将文档 ID 列表或聚合结果写入独立 Key，同时设置合理 TTL。

```text
search:cache:{queryHash} -> [doc:12, doc:31, doc:48]
```

规范化时要固定参数顺序、大小写、默认值和分页参数，否则同一个查询会算出不同哈希。缓存值建议只存文档 ID，展示时再用 `MGET` 或重新查询取内容，避免把整份文档快照长期留在缓存里。

这时要同时考虑数据更新后的失效策略：

- 结果允许短时间不一致，可以使用较短 TTL，用时间换实现简单；
- 要求强一致，就需要在写入业务数据时精确删除相关缓存，而维护成本会明显上升；
- 缓存击穿要单独处理，例如同一查询只允许一个请求回源，其余请求等待结果。

## 什么时候不该缓存

如果索引设计正确、过滤条件收敛、分页受控，直接查询通常已经足够快。此时增加一层结果缓存，会引入失效逻辑、内存增长和一致性问题，收益却不明显。

可以先观察真实延迟分布，再用 `FT.PROFILE` 看查询计划和各阶段耗时。只有当聚合确实昂贵、访问高度重复，并且团队能接受明确的一致性策略时，再增加业务缓存。

## 实际选择

先直接查询并观察延迟；确认瓶颈在查询执行而不是网络或文档加载后，再考虑缓存。需要长期复用的结果，交给业务层显式管理；RediSearch 自己保存的是索引，不是你的查询结果。
