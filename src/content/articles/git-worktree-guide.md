同时处理两个需求时，最直接的办法是复制一份项目目录，再切换到另一个分支。Git Worktree 也会创建另一个工作目录，所以两者看上去很像：都能让两份代码同时存在，都能在各自的编辑器里打开。

真正不同的是，复制目录复制的是整个仓库，而 Worktree 只是给同一个仓库多开了一扇门。

## 核心区别

复制项目通常意味着复制整个 `.git` 数据库：提交历史、对象、引用、配置全部再来一份。之后两个目录各走各的，远程更新、分支状态、标签都需要分别维护。

Worktree 则让多个工作目录共享同一个 Git 对象库。每个工作区只拥有自己的工作文件、暂存区和 HEAD，提交、分支、标签、远程引用都指向同一份数据。

```text
同一个仓库
├── 主工作区          main
├── .worktrees/blog   feature/blog
└── .worktrees/fix    hotfix/login
```

在最常见的目录形态里，主工作区的 `.git` 是一个目录；附属工作区里的 `.git` 则是一个文本文件，内容指向主仓库的 `worktrees/<name>` 元数据。这也是某些旧脚本误判“这里不是 Git 仓库”的原因。

Git 会阻止同一分支同时被两个 Worktree 检出。两个目录不会各自持有一份同名分支，也就少了一类“在 A 目录提交、B 目录却显示旧状态”的混乱。

## Worktree 的优势

- 不重复下载完整仓库历史，磁盘占用主要是工作文件而不是对象库；
- 分支、提交和远程引用天然同步，`fetch` 一次所有工作区都能看到；
- 可以明确看到所有附属工作区，状态是集中可查的；
- 删除工作区时由 Git 清理关联元数据，不留悬空引用；
- 适合在主项目之外并行运行测试、复现问题或开发独立需求。

常用命令如下：

```bash
# 基于当前 HEAD 新建分支并检出到独立目录
git worktree add .worktrees/blog -b feature/blog

# 检出一个已经存在的分支
git worktree add .worktrees/fix hotfix/login

# 只查看某个提交，不占用分支（分离 HEAD）
git worktree add .worktrees/review 3f2a1c9

git worktree list
git worktree remove .worktrees/blog
```

`git worktree remove` 在目录有未提交改动时会拒绝执行，确认不再需要时可以加 `--force`。如果目录是被手动删除的，用 `git worktree prune` 清掉残留记录。放在移动硬盘或网络盘上的工作区，可以用 `git worktree lock` 防止被误清理。

## 容易踩的坑

**分支唯一检出**：同一个分支不能同时出现在两个工作区。需要并行改同一分支时，要么拆成两个分支，要么接受其中一个是分离 HEAD，后者不适合直接提交。

**共享的不只是对象库**：stash、hooks、大部分配置都属于公共部分。在 A 工作区 `git stash`，B 工作区也能看到同一条记录；钩子改一次，所有工作区一起生效。把 Worktree 当成完全隔离的沙箱会判断失误。

**依赖和环境不共享**：`node_modules`、虚拟环境、构建缓存、`.env`、本地数据库都要各自准备。两个工作区同时跑 `docker compose up` 还会抢占同一组端口。

**子模块要单独初始化**：新工作区不会自动带出子模块内容，需要执行 `git submodule update --init`。

**目录位置要明确**：把工作区放在主仓库内部时，记得把 `.worktrees/` 加进 `.gitignore`，否则主工作区会把它当成未跟踪文件。更稳妥的做法是放在仓库的兄弟目录。

**IDE 索引各自独立**：两个目录会被编辑器当成两个项目，索引、插件状态、调试配置都要分别维护。这不是故障，但会占用额外内存。

## 什么时候直接复制或 Clone

如果需要彻底独立的 Git 历史、不同的远程仓库、不同的权限边界，或者要把目录交给无法访问原仓库的人，独立 Clone 更清晰。CI 里也通常直接 Clone，避免工作区状态互相影响。

仅仅为了并行开发不同分支、跑测试或临时验证一个提交，Worktree 更轻、更安全：对象只存一份，分支状态集中管理，清理也有明确命令。

## 小结

复制目录得到的是两个互不相关的仓库；Worktree 得到的是一个仓库的多个视图。前者适合彻底分家，后者适合短期并行。判断标准不是“哪个命令短”，而是这段代码以后还要不要共享同一份历史和远程状态。
